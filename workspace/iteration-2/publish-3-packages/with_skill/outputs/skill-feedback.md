# Skill feedback: haiku-delegate, publish-3-packages dry run

## Where I had to guess

1. **The tag-triggered publish workflow that can't work.** "Releases where CI publishes" and the last bullet ("decide which one publishes ... and ask the user if it isn't clear") assume the workflow is a working alternative. Here every repo has `release.yml` on `v*` tags running `npm ci && npm run build && npm publish --provenance`, but there's no lockfile (so `npm ci` dies) and `build.js` doesn't produce `dist/cli.js` (so even a fixed CI would ship a package without its bin). The skill doesn't say what "clear" means. I decided it was clear: the user said "already-built", and CI can't publish. So no question, just a heads-up. Suggest one sentence: "If the workflow can't succeed (no lockfile for `npm ci`, a build that doesn't produce what `files`/`bin` need), the local publish is the publisher; mention the broken workflow at wrap-up instead of asking." Also suggest a preflight check for the deciding fact: how the previous version was published (`npm view <pkg>@<prev> _npmUser.name dist.attestations`). Nothing in the skill tells you to look at release history on npm, and it's the best evidence of which path the user really uses.

2. **The race is prevented by ordering, and the skill never says so.** It says to "decide which one publishes", not how the decision stops the race. What actually stops it: publish locally first, push the tag only after the publish landed, in an agent that stops before the tag push if the publish failed. Then CI hits "version exists" (E403). Example 1 has this order, but it's never stated as the rule. A main model could easily write tag-then-publish (the "release chain" in step 1 even lists "publish → tag", but as a convention, not as the race guard). Suggest stating it in step 2's third bullet.

3. **Gitignored build output isn't pinned by anything in the template.** Example 1's guard is `git status --porcelain` plus HEAD = SHA. When `dist/` is in `.gitignore` (very common for built packages), that guard says nothing about what gets published. I added a step to each publish brief: `npm pack --dry-run --json --ignore-scripts`, which must show the exact integrity and entryCount I recorded at review time. After the publish I check `npm view ... dist.integrity` against the same value. SKILL step 5 already mentions the integrity comparison afterwards; the template should add the *pre-publish* integrity check as a standard step, at least whenever `files` includes gitignored paths.

4. **Existing-version preflight.** The worked example's preflight is "names free (`npm view <pkg>` should return E404)". These packages already exist, so that check is wrong here. The useful checks are `npm view <pkg> versions --json` (the new version absent, nothing newer) and `npm owner ls`. Worth one line: new packages → E404 on the name; existing packages → version absent + you're an owner.

5. **2FA preflight is incomplete.** The skill only names `npm profile get --json` → `auth-and-writes`. A package-level setting (`npm access get mfa <pkg>` → `publish`) also forces an OTP on every publish, whatever the account's setting is. I check both. Also, `npm publish </dev/null` doesn't stop at a browser-auth prompt: npm prints an "Authenticate your account at ..." URL and polls, so the command hangs until the Bash tool times out. The agent then sees "tool timed out", not "browser approval", and the template's stop conditions route that to "stop and report" (`failed`, probably), not `NEEDS_USER`. I added a sentence to the publish step telling the agent that a timeout with an auth URL in the output is `NEEDS_USER`. The template's browser/2FA stop condition should say this outright.

6. **Tag convention vs commit convention.** "Take tag names and messages from the repo's existing tags" covered the tag (annotated, message = tag name). But the previous tags sit on `release: vX` commits, and this HEAD is `chore: bump to X`. Matching the commit convention would mean a new commit and a push to main, which isn't approved. I tagged HEAD as is and noted it. The skill could say: "follow the tag convention; don't create a release commit to match history if it means a push nobody approved."

7. **How many agents for 3 tiny packages.** The cost guidance ("one or two quick commands are cheaper to run yourself", "For two or three small packages, run them yourself" for pack/scan) pulls one way. The worked example ("Install check, one agent per package") and the user's "verify installs" request pull the other. I ended up with 6 cold-start agents (3 publish+tag, 3 install) for packages that are 4 files each. I followed the worked example because install checks are listed Haiku work and each has its own gate. But the skill never says whether install checks for small packages fall under the "run them yourself" rule, or whether two install checks whose gates are met together should share one agent. A rule of thumb would help: "merge items whose gates are met together into one agent unless a failure in one should not block the other."

8. **Gate for the dependent publish: npm-verified or install-verified?** The worked example gates cli on "core + utils verified on npm", not on their install checks. I followed it. But a dependent publish is irreversible, and the dependency's install check is cheap, so a careful model might reasonably wait. Saying why the example doesn't wait (a broken dep gets fixed forward with a patch the `^` range picks up) would remove the doubt.

9. **Annotated-tag verification.** The verify table checks `gh api repos/<o>/<r>/commits/<tag> --jq .sha`, which peels to the commit. That doesn't catch a lightweight tag, or a different tag object on the right commit. I added `gh api repos/<o>/<r>/git/ref/tags/<tag> --jq .object.sha` → the tag object SHA from the brief. Cheap; suggest adding it to the table.

10. **Task-list size.** The session's task-list tool takes at most 12 items. With per-package gates (separate publish, verify and install lines per package) this plan wanted 13+. I merged "verify fmt" and "verify lint" into one line. The worked example (10 lines for 5 packages) gets around this by batching rows ("4 agents" on one line), but then it loses per-item gates, which step 1 says every delegated step needs. Say which one wins: batching rows with a per-item gate in the text is fine.

11. **Preflight order vs local tags.** The worked example makes local tags after the repos are verified. The skill doesn't say that local tags should wait for a read-only network preflight (origin/main = HEAD, tag name free on the remote), though Example 1 assumes it ("main already pushed at 3f9c2a7…"). I put tagging behind the network preflight. (In this dry run I made the tags on assumed-good preflight results, since network was off-limits.)

## Things I did that the skill didn't say

- I added the integrity pin (point 3), the `NEEDS_USER`-on-timeout line (point 5), and a dependency re-check step in the cli brief (`npm view` of fmt and lint 1.2.0 before publishing). The skill puts that guard in the gate only; with it also in the brief, a launch made too early stops by itself.
- I added extra Do-not lines to the publish briefs: no `npm run build`, `npm install`, `npm ci`, `npm version`, `npm dist-tag`, `npm access`, `npm trust`, non-dry-run `npm pack`, `gh release create`. The obvious "fixes" a cold agent might reach for if the integrity check fails are rebuilding or reinstalling, which would change the tarball.
- The install briefs say "leave the temp folder in place" and "don't touch anything under the repo folder". The template's file rule ("only inside the temp folder") doesn't stop cleanup with `rm -rf`, which agents like to do at the end.
- The `added N packages` count in the install briefs is a soft expectation (a line starting with `added`; the exact version check comes from `npm ls`). A strict `added 3 packages` would make the agent stop over npm's counting quirks, which tell you nothing.

## Small wording issues

- Template Example 1's Do-not "Do not edit, create or delete files except: none" reads awkwardly; "Do not edit, create or delete any files." is clearer.
- "Name the shell" says Git Bash uses `/c/Users/...` paths, but doesn't warn that real Windows paths often contain spaces (here `github repo`). The quoting rule covers it, but the worked example's paths have none, so it's easy to forget to say so in Inputs. I added "The path contains a space, so keep the double quotes."
- The SKILL step 2 heads-up instruction ("mention it in one line when you launch") and wrap-up "(Each repo shows one failed `release` run ...)" worked well as written; no change needed.
